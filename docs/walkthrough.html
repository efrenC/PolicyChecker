Step 1 of 8

Guard the door

app.py · GuardMiddleware

Before FastAPI sees anything, a small piece of middleware checks the size of the request body. The limit is 16 KB, which is far more than four datasets need.

If the client declares a size, that number is checked first. If it doesn't, the body is read in chunks and counted as it arrives, so a client can't get around the limit by leaving the size out. The body is then replayed to FastAPI unchanged.

The same middleware adds two security headers to every response on the way back out.

Turned away here: bodies over 16 KB get 413 and an audit entry. The oversized body itself is never stored.

Step 2 of 8

Validate the input

models.py · ClassificationRequest, Dataset

FastAPI parses the JSON into the Pydantic models. The models are strict, and they check everything about the shape of the request in one pass:

between 2 and 4 datasets; a name and description that aren't blank once spaces are trimmed, and aren't too long; one of the four known levels; a policy link that is a valid URL and uses HTTPS; and no fields the service doesn't recognise.

Pydantic collects every problem it finds, so the caller sees all of them at once instead of fixing one per attempt.

Turned away here: anything that fails returns 422 with the full list of problems and an audit entry (app.py · audit_invalid_request).

Step 3 of 8

Hand off to the pipeline

app.py · classify_datasets

The endpoint itself is short. It converts the validated models back into plain dictionaries, calls the pipeline, and translates the outcome into an HTTP response.

mode="json" matters here: it turns Pydantic's URL objects back into plain text. Leaving it out is what made every request fail with a 500 in the original version of this code.

Two ways out: a ClassificationRejected from the pipeline becomes 400, already audited. Any other error is logged for the operator and the caller gets a generic 500 with no internal details. A crash is the one outcome that doesn't get an audit entry.
Step 4 of 8

Re-validate inside the pipeline

classification_graph.py · validate_datasets

The pipeline runs the business rules again. Through the API this is redundant, because step 2 already caught everything. It's there because the pipeline can also be called directly, by a batch job or another agent, without the API in front of it.

The pipeline keeps its working data in one dictionary, ClassificationState. Each step reads it, adds one key, and passes it on. This step adds validation.

Turned away here: failures are written to the audit log with stage pipeline, then raised as ClassificationRejected, which step 3 turns into a 400.

Step 5 of 8

Check every policy link

classification_graph.py · check_policy_links
link_checker.py · http_link_checker

Each dataset's policy link is checked to confirm it actually leads somewhere. All the links are checked at the same time on separate threads, so three slow sites cost one timeout, not three.

This is also where the service could be abused. It fetches addresses supplied by callers, so a caller could point it at an internal system. The checker therefore vets every address before connecting, and does it again after every redirect.

A failed or blocked link doesn't stop the request. It's reported in the response, and the classification still goes ahead.

An address counts as public only if it isn't in a private, loopback, link-local (which includes the cloud metadata service at 169.254.169.254), carrier-grade NAT, multicast or reserved range. IPv6 addresses that wrap an IPv4 address are unwrapped first. If a host resolves to several addresses, all of them must be public.

Step 6 of 8

Apply the max-risk rule

classification_graph.py · compute_max_risk
classifications.py · SECURITY_ORDER

The core rule of the service is a single max() call. Each level has a rank, from Public (1) to Restricted (4), and the combined data takes the highest rank among the inputs.

The ranks come from the order the levels are listed in classifications.py. Changing the scheme means editing that one list.

Step 7 of 8

Write the audit entry

classification_graph.py · write_audit_log
audit.py · append_audit_entry

The full decision is appended to audit_log.jsonl as one line of JSON: the inputs, the validation result, every link check, and the classification. It gets a random unique ID and a UTC timestamp.

A lock makes sure two requests finishing at the same moment can't interleave their lines. Because each entry is written as encoded JSON, a dataset name containing a line break can't forge a fake entry.

Rejections use the same writer: audit_rejection calls append_audit_entry with outcome rejected, the stage that refused the request, and the errors.

Step 8 of 8

Respond

classification_graph.py · return_result
models.py · ClassificationResponse

The state is reshaped into the response format and checked one last time against the response model, so the service can't send back something its own contract doesn't allow.

The caller gets 200 with the classification, every link result, and the audit ID it can quote later. The two security headers from step 1 are added on the way out.
